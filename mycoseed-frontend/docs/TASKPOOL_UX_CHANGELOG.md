## TaskPool/Semi UX 改动清单（持续更新）

写法：每条都记录「我推断你怎么想」→「现状哪里不友好」→「我怎么改」。

### 2026-04-17

- **方案A：普通任务隐藏“任务池感”（只换文案，不改结构）**
  - **推断意图**：你希望普通任务看起来就是“普通任务”，不要让用户看到“任务池/TaskPool/Manager”等术语；同时又要保持代码结构简洁，不分两套链路。
  - **不友好点**：普通任务走的是 TaskPool 底层机制，但 UI 直接暴露“任务池管理”等术语，用户会困惑且觉得“丑”。
  - **改动**：管理页标题改为「链上进度与结算」，按钮与回调页主入口统一为「查看链上进度/下一步」，并将「撤回任务池/编辑任务池」等字眼替换为对用户更直观的表达（不改路由/合约/回跳）。

- **领取/审核 Semi 回跳带上 taskInfoId，回调页主按钮直达任务池管理**
  - **推断意图**：领取、审核之后，用户最常需要的是看「整单进度」和后续终审/结算，而不只是回到单条任务详情。
  - **不友好点**：`semi-claim-callback` / `semi-approve-callback` 只有「回任务详情」，与预付回调页的「去任务池管理」不一致；从详情页也难以一眼看到全链路状态。
  - **改动**：`[id].vue` / `review.vue` 构建回跳 URL 时追加 `taskInfoId`；两页回调增加主按钮「去任务池管理（进度/下一步）」与简短「下一步」说明文案。
- **终审/结算回调页补齐浏览器链接与公示期说明**
  - **推断意图**：用户需要能自查链上交易，并理解「为什么还不能马上结算」。
  - **不友好点**：`semi-final-approve-callback` / `semi-distribute-callback` 仅有 tx 文本，无浏览器入口；终审成功后容易误以为立刻可以 distribute。
  - **改动**：成功态增加 Optimism 浏览器链接；终审成功提示约 24h 公示；两页增加失败/异常时的 `recoveryHint`；主按钮文案与预付页风格对齐（去任务池管理…）。
- **任务池管理页：终审/结算用人话 + 禁用原因可解释**
  - **推断意图**：普通任务发布者不需要记合约函数名；需要知道公示期与按钮灰掉的真实原因。
  - **不友好点**：按钮文案含 `finalApprovePool`/`distribute`；灰掉时只写「需创建者且已建池」，未区分未登录/非创建者/未建池/已关闭；元数据区英文枚举不友好。
  - **改动**：说明改为「终审 → 约 24h 公示 → 结算」；按钮改为「终审（开启公示）」「结算（链上发放）」；`taskpoolPhase` 显示中文标签；`finalApproveDisabledHint` / `distributeDisabledHint` 分情形提示；toast 去掉生硬合约名；全页「仅 Manager …」统一为「仅负责人…」。

### 2026-04-16

- **发布普通任务后自动进入管理页**
  - **推断意图**：你想要“用户只点一次发布，然后在一个明确的地方看到链上进度/下一步”，避免用户迷路。
  - **不友好点**：`/tasks/create` 打开 Semi 弹窗后，当前页停在表单，用户不知道该去哪看 `tx_hash/phase`、也不知道下一步（领取/审核/终审）入口在哪里。
  - **改动**：发布时打开 Semi 后，当前页面自动跳转到 `/tasks/pool/:taskInfoId/manage?focus=semi-prepay`，让用户在管理页看到“预付/建池状态”和后续按钮。
- **Semi 预付回调页增加“下一步”强引导**
  - **推断意图**：你希望回调页不仅是“结果展示”，还要把用户带回“能继续操作”的页面（管理/详情）。
  - **不友好点**：回调页信息多但动作弱，用户容易停在回调页不知道下一步。
  - **改动**：回调页优先展示“去任务池管理页查看建池状态/重试”的主按钮；若能从发布草稿恢复到 taskId，则提供“回任务详情”按钮。
- **审核页移除调试上报噪音**
  - **推断意图**：线上用户不应被 debug 行为影响；你要的是稳定、可解释、可回跳的 Semi 流程。
  - **不友好点**：`review.vue` 中残留 `fetch('http://127.0.0.1:7242/ingest/...')` 与大量 console 调试，会导致不必要网络请求/隐私风险/控制台噪音。
  - **改动**：删除这些 debug 上报与多余 console.log，保留必要的错误提示与 toast。
- **领取时遇到“建池未确认”给出人话提示并引导到管理页**
  - **推断意图**：你希望“链上成功是强依赖”，用户不应该在未建池确认时还被允许去 Semi 领取；同时也不该只看到一个 409 生硬报错。
  - **不友好点**：任务详情页点领取时，如果后端 `claim-intent` 返回 409（未写入 `taskpool_create_tx_hash`），用户只看到失败 toast，不知道下一步。
  - **改动**：捕获 `getTaskpoolClaimIntent` 的 409 文案，替换为更直观的提示，并自动跳转到该任务的任务池管理页查看建池状态。
- **发布页移除多余 console 调试输出**
  - **推断意图**：你想要的是“对用户透明的流程”，而不是让用户/运营在控制台里看到不必要的内部日志。
  - **不友好点**：`create.vue` 在选择用户/发布时输出多段 console.log，既噪音又可能泄露用户选择信息。
  - **改动**：移除这些 console.log，保留必要的错误提示与 toast。
- **管理页 Semi 预付卡片避免误导普通任务用户**
  - **推断意图**：普通任务发布应“一键完成预付+建池”，管理页不应让用户以为还要再做一遍预付。
  - **不友好点**：管理页的「链上预付」卡片标题/文案容易让人误解它是“必须步骤”，但它其实只做入金 credit，不建池。
  - **改动**：明确标题为“仅入金 credit”，并在文案里说明：普通任务发布页通常已完成「预付+建池」，这里主要用于未建池草稿补齐入金。
